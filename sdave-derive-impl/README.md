# sdave-derive-impl

The public codegen internals of `sdave-derive`: every token stream the SDAVE derive macros emit is
built here.

It exists because a `proc-macro` crate may only export proc macros. Keeping the generators in a normal
library crate is what lets them be public, documented and unit-tested at all, so `sdave-derive` is a
thin wrapper and this crate is where the work happens.

Each document owns one layer: the wire format the generated impls produce is `sdave-codec/README.md`'s,
the macro surface a user sees is `sdave-derive/README.md`'s, and the codegen itself is this file's.

## Not an application API

Published because `sdave-derive` must depend on it at the same version, not because an application
should call it. Its functions are public, documented and stable enough to be audited, but they are the
*implementation* of the macros: expect them to change with the codegen, and do not build a codec on top
of them.

## Module map

| module | holds |
| --- | --- |
| `lib` | the shared identifiers and path helpers, and the `Variants` alias |
| `field` | `FieldInfo`, one field's codegen metadata, and the `#[default]`/`#[skip]` attributes |
| `generics` | echoing the annotated type's generics into an impl, field-type bounds, the `TypeName` impl |
| `slices` | the compile-time `SLICES` counts (`struct_slices`, `enum_slices`) |
| `serialize` | `expand_serialize` and the `serialize` bodies it composes |
| `deserialize` | `expand_deserialize` and the field-matching bodies it composes |
| `dyn_trait` | `expand_sdave_dyn`, the `dyn Trait` impls and the sealing marker |
| `tests` | the unit tests, comparing token streams and data helpers |

`lib` re-exports all of it at the crate root, so `sdave_derive_impl::expand_serialize` and the module
path reach the same function. `sdave-derive` and `sdave-derive-impl` are released in lockstep at the same
version: the wrapper parses the input item and forwards it, and holds no generator logic of its own.

This crate depends on `syn`, `quote` and `proc-macro2` only — never on `sdave-codec`. The codec is a
*path* in the emitted tokens, not a dependency, which is what lets the whole codegen be unit-tested
without building a codec.

## Conventions the generated code follows

A generated impl is ordinary Rust written for a crate whose dependency is called `sdave_codec`, and it
is written so that nothing in the annotated crate can capture its names:

- **Paths are absolute**: `::sdave_codec::Serialize`, `::core::option::Option`, `::core::result::Result`.
  A user `struct Serialize;` cannot shadow a path that starts at the crate root.
- **Allocator/vec aliases go through `__private`**: `::sdave_codec::__private::{Box, Global, Vec}`, a
  `#[doc(hidden)]` module of `sdave-codec` that only guarantees those paths stay stable.
- **The allocator parameter is `__SDAVE_A`** and the name-policy parameter is `__SDAVE_N`
  (`allocator_ident`/`policy_ident`). Both are legal (if unusual) identifiers, so the generated impl can
  never collide with a generic parameter of the annotated type.
- **Locals and bindings are `__sdave_*`**: `__sdave_head`, `__sdave_slices`, `__sdave_cursor`,
  `__sdave_signature`, `__sdave_payload`, `__sdave_items`, `__sdave_value`, `__sdave_inner`, and a
  positional binding `__sdave_field_<n>` per field. The underscore prefix also keeps a binding that a
  `#[skip]`ped field never reads out of the `unused_variables` lint.
- **The sealing trait is `__SdaveDynClaim_<Trait>`**, `#[doc(hidden)]` and non-camel-case-allowed.

## `cargo expand` order

Each `#[derive(Serialize)]` emits, in this order: the `TypeName` impl, the `Serialize` impl (holding
`serialize` and `serialize_typed`), and nothing else. `#[derive(Deserialize)]` emits one `Deserialize`
impl. `#[sdave_dyn]` emits the sealing trait and one `impl` of it per claimed type *before* the annotated
trait, then the trait-object impls listed in `sdave-derive/README.md`.

`serialize_typed` is generated by the same helper (`serialize_typed_method`) for the derives and for
`#[sdave_dyn]`, so the typed layout lives in exactly one place.

## `SLICES` accounting

Every slice count is independent of the allocator, which is what lets the derive evaluate a field's
`<FieldTy as Serialize<u8, _>>::SLICES` through the concrete `Global` while the impl itself stays
generic over `__SDAVE_A`: a projection off a generic parameter is not a constant.

- **A struct** costs `2 + Σ(1 + SLICES_i)` over its *encoded* fields — the outer limiter and delimiter,
  then one signature plus one value Envelop per field. `#[skip]`ped fields contribute nothing.
- **An enum** costs the maximum over its variants: `3` for a variant with no fields at all, and
  `2 + Σ(1 + SLICES_i) + 3` for a variant with fields (the extra 3 being its inner Envelop). The unused
  tail of the array stays `None` padding, which the core's `Slices` view ignores.
- **`SlicesTyped` is `Slices + 3`**: the outer limiter, the `name: type` signature and the outer
  delimiter.
- **A type with type/const parameters** cannot size the array from its fields and instead reports the
  fixed `3`/`6` every flattened shape uses, flattening its fields in place like an iterable.

The two paths are the same codegen with a different tail: the monomorphic path records each field's
slices in the array and frames the array once, the flattened path concatenates each field's logical
bytes in place and frames the region once.

## One shape, one helper

Where a shape could be emitted twice it is emitted once, so a change to the wire format cannot apply to
half the cases:

| helper | shape |
| --- | --- |
| `field_signature` | one field's `NonEnvelop` text (`signature_prefix ++ rendered type ++ signature_suffix`) |
| `field_serialize_loop` / `field_flatten_loop` | the per-field signature + value pair, unflattened / flattened |
| `enum_serialize_arms` | the `match self` arms, one per variant, for both enum bodies |
| `parse_fields` | decoding the `NonEnvelop ++ Envelop` pairs, by signature or by position |
| `constructor` / `fieldless_constructor` | the value expression a deserializer returns |
| `serialize_typed_method` | the typed wrapper, shared with `#[sdave_dyn]` |
| `slices_type` / `global_allocator` | the `[Option<(Offset, Offset)>; n]` array type and the concrete allocator used to evaluate `SLICES` |

## Testing

`src/tests.rs` unit-tests the helpers directly: token streams are compared after stripping whitespace,
data helpers (`FieldInfo`, `is_any_bound`, …) by value. That pins the generator's output, not the
generated program.

The generated programs are pinned in `sdave-codec/tests/derive.rs`, where the derive and the codec are
both in scope and every shape is serialized, deserialized and compared. `sdave-codec/tests/features.rs`
does the same for the feature-gated shapes.

```sh
cargo test -p sdave-derive-impl     # the token streams
cargo test -p sdave-codec           # the generated impls, at run time
```

The crate is `#![no_std]` outside `cfg(test)`, and its tests use `alloc` only.
